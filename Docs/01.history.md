# 项目历史与经验

## 初始基线

- 项目目录原先只有 `Docs/02.orchestrator-implementer-architecture.md`，没有 Git 仓库，也没有游戏代码。
- 已初始化 Git，避免后续无法审查真实 diff 或回退。
- OpenCode 可用模型标识为 `opencode/deepseek-v4.1-flash-free`，与用户指定的 DSV4.1 Flash 对应。
- 架构强调“先读 diff、再独立验证、最后读报告”，后续 Review 必须按此顺序执行。

## [Orchestrator]

- 设计阶段先确认了范围、视觉方向和技术方案，避免 Implementer 在手机优先与桌面布局之间自行猜测。
- 将“开始/重开后焦点移回棋盘”和空格键 `' '`/`Space` 兼容写入契约，提前消除键盘失效风险。
- 设计规格与实施计划分别保存，计划以 TDD 步骤和可复现命令约束 Implementer。

## [Implementer]

- 先写测试并实跑 RED 能暴露真实缺口：Task 2/3 的 RED 是模块不存在，Task 4 的 RED 是 `createGame` 未导出，避免了“只写测试不运行”的假 TDD。
- 墙踢测试最初把 I 方块的第二次旋转误当成回到旋转 0；实际 4×4 矩阵下 I 的旋转 1→2 仍是竖向但列偏移不同，修正测试期望而不是改实现。
- 硬降测试最初按 O 方块占第 3/4 列断言，实际 4×4 出生矩阵占第 4/5 列；以真实矩阵为准修正断言。
- 行清除集成测试使用种子 1 的前四块 `O J L S`，按 `x=-1/2/7/5` 摆放可稳定清 1 行，总分 268（四个硬降 42×4 + 100），使状态机测试可完全脱离计时器。
- 移动端布局的瓶颈是宽度而不是高度：390px 视口下侧栏压缩后棋盘为 240×480；通过固定 1:2 比例与 `max-width` 避免溢出，触控键保持 50px 高。
- 初始焦点放在覆盖层按钮上，开始/重开/暂停按钮操作后统一回到棋盘 Canvas，保证键盘立即可用且按钮聚焦时不会误触游戏动作。

- 出生可见性缺陷的根因不止 `y = 0`：I 方块的实心行在 4×4 矩阵索引 1，即使出生 `y = 2` 仍完全位于隐藏区。修复时把出生改为 `HIDDEN_ROWS - 2`，并将 I 的实心行下移到索引 2，使 7 种方块出生时都至少有一格可见。
- 出生下移后，同一四块序列的硬降距离由 21 变为 19，清行集成总分由 268 调整为 252；回归测试仍断言精确分数，未降低规则强度。
- 浏览器验证使用 Canvas 像素采样而不是只看截图：按种子 0/1/2/4/8/9/14 覆盖 7 种方块，检查可见区首行的实心格，避免「O 可见即全部通过」的假阳性。
